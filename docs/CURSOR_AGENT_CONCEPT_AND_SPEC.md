# Cursor-агент проекта «Нота Миру»: концепция и техническое задание

Статус: черновик для обсуждения
Версия: 0.1
Связанные документы:
- `tools/telegram-cursor-agent/docs/telegram-bot-specification.md` — спецификация Telegram-канала запуска агента;
- `AGENTS.md` — операционные правила агента в репозитории (артефакт фазы 1 этого ТЗ);
- `ROADMAP_2026.md`, `DETAILED_ROADMAP.md` — продуктовый контекст.

---

## 1. Концепция

### 1.1. Что такое Cursor-агент «Нота Миру»

Cursor-агент — это штатный AI-разработчик проекта, который выполняет инженерные
задачи по кодовой базе `notameru2026` автономно: читает код, вносит изменения,
прогоняет проверки, оформляет результат в виде коммитов и pull request, а в
Telegram-контуре — в виде понятного человеческого отчёта.

Агент — не чат-бот и не генератор советов. Его результат всегда материален:
изменённые файлы, PR, отчёт о диагностике, обновлённая документация.

### 1.2. Зачем он проекту

Редакция «Нота Миру» — небольшая команда, в которой разработка конкурирует за
время с контентом и продуктом. Агент закрывает три потребности:

1. **Скорость рутины.** Багфиксы, миграции, мелкие фичи админки, правки
   шаблонов и SEO-логики выполняются без ожидания свободного разработчика.
2. **Доступность из любого места.** Главред или редактор ставит задачу из
   Telegram голосом или текстом — агент выполняет её на сервере.
3. **Память проекта.** Агент работает по писаным правилам (`AGENTS.md`),
   поэтому каждая задача выполняется в одних и тех же конвенциях, а не «как
   получится».

### 1.3. Ключевой принцип

> Один агент — три контура запуска — одни правила.

Поведение агента определяется не тем, откуда он запущен, а едиными правилами в
репозитории. Telegram-бот, Cloud Agent с GitHub и локальный Cursor IDE — это
только транспорты для постановки задач.

## 3. Роль и границы ответственности

### 3.1. Агент делает

- разработка и рефакторинг кода Laravel/PHP/JS/Blade;
- миграции БД (создание файлов; запуск — только через approval);
- тесты PHPUnit (написание и прогон);
- диагностика: логи Laravel, 404-логи, SEO-аналитика, ошибки админки;
- документация: гайды в `docs/`, README, runbook'и;
- подготовка PR и ревью чужих PR по запросу;
- работа с macOS-клиентом (SwiftUI) и notame-agent (Node.js) в пределах репозитория.

### 3.2. Агент не делает без явного подтверждения человека (approval-flow)

- деплой на production;
- запуск миграций на боевой БД (`artisan migrate` на сервере);
- операции с systemd, nginx, PM2, cron;
- удаление файлов и данных;
- `composer install/update`, `npm install` на сервере;
- destructive git: `reset --hard`, `clean`, `push --force`;
- любые операции с секретами, токенами, паролями, `.env`.

### 3.3. Агент не делает никогда

- не выводит секреты в чат, логи, коммиты и отчёты;
- не коммитит `.env`, дампы БД, архивы, артефакты сборки;
- не выдумывает факты о проекте: если контекста не хватает — задаёт короткий
  уточняющий вопрос вместо «галлюцинации»;
- не принимает редакционные решения (что публиковать, как править тексты
  статей) — это зона notame-agent и людей.

### 3.4. Разграничение с notame-agent

| | Cursor-агент | notame-agent |
|---|---|---|
| Предмет | код, инфраструктура, документация | контент, статьи, фото, соцсети |
| Меняет кодовую базу | да | нет |
| Меняет контент сайта | нет (кроме шаблонов/логики) | да |
| Канал | Telegram-бот kit, GitHub, IDE | свой Telegram/веб-интерфейс |

Если notame-agent сталкивается с багом — он (или человек) ставит задачу
Cursor-агенту, а не правит код сам.

## 4. Контуры запуска

### Контур A — Cursor IDE (локальная разработка)

Разработчик работает в Cursor на своей машине. Агент подчиняется `AGENTS.md` и
`.cursor/rules`. Это базовый контур, дополнительная разработка не требуется —
нужны только файлы правил (фаза 1).

### Контур B — Cloud Agents (GitHub)

Задачи ставятся из Cursor Web/Dashboard или по упоминанию в GitHub. Агент
работает в изолированной VM с клоном `arhangelskydmitry/notameru2026`,
результат — всегда ветка `cursor/*` и draft PR. Деплоя из этого контура нет:
изменения попадают на сервер только после merge и ручного (или одобренного)
деплоя.

Требования:
- база — ветка `main`, ветки именуются `cursor/<задача>-<суффикс>`;
- перед PR агент прогоняет доступные проверки (`vendor/bin/pint --test`,
  `php artisan test`, для Node-частей `npm run typecheck && npm run build && npm run test`);
- PR содержит: что сделано, как проверено, что осталось/риски.

### Контур C — Telegram-бот (production-сервер)

Реализован в `tools/telegram-cursor-agent`. Особенность: агент работает **прямо
в боевой директории** (`WORKING_DIRECTORY=/srv/.../current`), поэтому контур
обвешан защитами:

1. перед каждой задачей — snapshot git-visible файлов (`BackupService`);
2. после задачи — `changedFiles` + `diffSummary` в карточке задачи;
3. `/rollback last` для approver-пользователей;
4. approval-flow для рискованных операций;
5. очередь: одна задача Cursor Agent одновременно.

Этот контур предназначен для **малых и средних задач** (правка шаблона, фикс
бага, диагностика). Крупные изменения (миграции схемы, рефакторинг модулей,
зависимости) должны уходить в контур B с ревью через PR. Классификацию размера
задачи делает сам агент и сообщает пользователю, если задача слишком крупная
для production-контура.

## 5. Жизненный цикл задачи

```
Постановка → Классификация → (Approval?) → Snapshot/Ветка → Выполнение
   → Самопроверка → Отчёт/PR → (Rollback при проблеме)
```

1. **Постановка.** Текст/голос/вложение в Telegram, prompt в IDE, задача Cloud Agent.
2. **Классификация.** Агент определяет: тип (фича/баг/диагностика/доки),
   рискованность (нужен ли approval), масштаб (production-контур или PR-контур).
3. **Подготовка.** Контур B/A: ветка `cursor/*`. Контур C: snapshot.
4. **Выполнение.** Сначала чтение существующего кода, потом изменения. Стиль —
   по паттернам проекта (см. `AGENTS.md`).
5. **Самопроверка.** Прогон тестов/линтеров, доступных в окружении; smoke-проверка
   затронутых страниц/команд, если возможно.
6. **Отчёт.** Контур B: PR с описанием. Контур C: короткий человеческий отчёт в
   Telegram — что изменилось, что проверено, какой практический результат, что
   нужно от людей дальше. Без task id, stack trace и «нейросимволов».
7. **Откат.** Контур C: `/rollback last`. Контур B: закрыть PR / revert.

## 6. Правила работы с кодом

Полные операционные правила — в `AGENTS.md` (корень репозитория), который агент
читает автоматически во всех контурах. Ключевые требования ТЗ к этим правилам:

- **стек**: Laravel 12, PHP 8.3, MySQL, Blade, MoonShine-админка, SwiftUI
  (clients/macos), Node.js/TypeScript (tools/telegram-cursor-agent);
- **паттерны**: бизнес-логика — в `app/Services`, тонкие контроллеры, хелперы в
  `app/Helpers` (регистрируются в `composer.json` → `autoload.files`);
- **миграции**: только аддитивные по умолчанию; именование по существующему
  шаблону `YYYY_MM_DD_HHMMSS_verb_subject.php`;
- **код на английском**, комментарии на русском — только когда реально поясняют
  неочевидное; коммиты — в стиле истории репозитория (русский или conventional
  `feat:/fix:/docs:`);
- **проверки перед сдачей**: `vendor/bin/pint --test`, `php artisan test`;
  для Node-частей — `npm run typecheck && npm run build && npm run test`;
- **документация**: новые гайды кладутся в `docs/`, а не в корень репозитория
  (корень уже перегружен историческими `*_FIX.md` — см. фазу 4).

## 7. Безопасность

1. **Секреты.** Источник — только env-файлы на сервере и Cloud Agents Secrets.
   В репозитории — только `*.example`. Агент никогда не печатает значения
   секретов; в логах они маскируются.
2. **Approval-flow.** Список рискованных операций — раздел 3.2. Pending approval
   с кнопками «Подтвердить/Отклонить», право подтверждения — только у
   `TELEGRAM_APPROVER_*` пользователей.
3. **Snapshot и rollback** в production-контуре — обязательны, задача без
   успешного snapshot не запускается (уже реализовано в `AgentRunner`).
4. **Доступ.** Telegram-бот отвечает только пользователям из allow-list
   (`ALLOWED_TELEGRAM_USER_IDS/USERNAMES`).
5. **Аудит.** Все события — в event log (JSONL) и журнале беседы; история задач
   хранится в task store в shared-директории.

## 9. Этапы внедрения

Этапы описаны по объёму изменений, без календарных оценок.

### Фаза 1 — Правила и единое поведение (этот PR)
- `AGENTS.md` в корне репозитория;
- данное ТЗ в `docs/`.
Инвазивность: нулевая, только документация.

### Фаза 2 — Контроль качества
- GitHub Actions: `pint --test` + `php artisan test` (sqlite in-memory) на каждый PR;
- наполнение `tests/Feature` смок-тестами ключевых маршрутов (главная, статья,
  категория, sitemap, RSS), чтобы агентские правки проверялись автоматически;
- скрипт `composer test` уже есть — используется как локальная точка входа.
Затрагивает: `.github/`, `tests/`, `phpunit.xml`.

### Фаза 3 — Регламент деплоя
- runbook: merge PR → деплой на сервер (git pull + кэши + опционально миграции
  через approval);
- команда `/deploy` в Telegram-боте как approval-операция (опционально).
Затрагивает: `docs/`, `tools/telegram-cursor-agent/apps/telegram-agent`.

### Фаза 4 — Гигиена репозитория (поддерживающая)
- перенос исторических `*_FIX.md`/`*_GUIDE.md` из корня в `docs/archive/`;
- удаление из git артефактов (`*.tar.gz`, `*.xlsx`, бэкапы в `docs/deploy-backup-*`)
  и дополнение `.gitignore`.
Затрагивает: корень, `.gitignore`. Риск низкий, но нужен отдельный PR.

### Фаза 5 — Развитие Telegram-контура (по потребности)
- автоматическая классификация масштаба задачи (production-фикс vs PR-задача);
- создание PR из Telegram-контура вместо прямой правки production для средних задач;
- сводка `/report` за день/неделю: какие задачи выполнены, какие файлы менялись.

## 10. Критерии приёмки концепции

Агент считается внедрённым, когда:

1. `AGENTS.md` существует и одинаково применяется во всех трёх контурах;
2. любой PR агента проходит автоматические проверки (pint + tests) в CI;
3. ни один секрет не попадает в репозиторий, чат или отчёты;
4. рискованные операции выполняются только через approval;
5. в production-контуре каждая задача имеет snapshot и возможность `/rollback last`;
6. отчёты агента понятны нетехническому пользователю (главреду);
7. крупные изменения проходят только через PR с ревью человека.

## 11. Открытые вопросы (на обсуждение)

1. **Модель.** Сейчас `CURSOR_MODEL=composer-2.5` в Telegram-контуре. Оставляем
   или поднимаем до более сильной модели для крупных задач?
2. **Порог «крупной задачи».** Формализовать, что уходит из Telegram-контура в
   PR-контур: миграции, изменения зависимостей, >N файлов?
3. **CI и БД.** Тесты в CI на sqlite или поднимать MySQL-сервис? (Часть кода
   может зависеть от MySQL-специфики.)
4. **Деплой.** Хотим ли автоматический деплой после merge в `main` (с approval
   в Telegram), или деплой остаётся полностью ручным?
5. **Второй бот-наставник** (`telegram-iiko-mentor`) — адаптировать под роль
   «продуктовый наставник Нота Миру» или удалить из kit?
